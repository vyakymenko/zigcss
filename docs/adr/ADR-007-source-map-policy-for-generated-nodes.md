# ADR-007: Source-map policy for generated nodes

- Status: Accepted
- Date: 2026-07-11
- Owners: ZigCSS emitter, transform, and source-map maintainers
- Roadmap: `MATH-001`, `OPT-012` through `OPT-015`, `PREFIX-002`, and later generated-output work

## Context

The lossless parser and emitter map surviving output from authored source spans. Semantic and compatibility transforms can instead create bytes that have no character-for-character source range: a folded `calc()` result, a synthesized shorthand, or an inserted compatibility declaration. Reusing an unrelated span, mapping every generated character to one authored character, or silently defaulting to source offset zero would make debuggers look precise while reporting false provenance.

The pass manager also needs a representation that distinguishes generated syntax from authored component values. A source map is an observability artifact, not proof that a rewrite is valid; transform-specific semantic validation remains mandatory.

## Decision

### Causal provenance

Every generated node that participates in mapping carries an explicit nonempty causal source span from the same `SourceFile` as its containing AST. The span identifies the smallest complete authored construct replaced or responsible for the generated syntax.

- A whole-value replacement, such as a folded math function, uses that authored value/function span.
- A generated declaration derived from one authored declaration uses the authored declaration span.
- A generated rule derived from one rule uses that authored rule span.
- A node derived jointly from multiple adjacent constructs uses their validated enclosing span and records the multi-input proof in its pass-specific metadata.
- If no honest causal source span exists, the generated segment receives no mapping. Offset zero or the preceding node must never be used as a fallback.

Generated payloads are structured AST data, not trusted raw CSS byte strings. Constructors validate finite/bounded fields and source containment; the emitter performs closed serialization and independently rejects invalid generated state.

### Mapping granularity

The emitter adds one mapping at the first generated byte of a generated segment, pointing to the start of its causal source span. It does not emit fabricated per-token or per-character mappings inside that segment. Authored syntax before and after the segment keeps its normal mappings.

For a rewritten declaration value, the declaration-name mapping remains at the declaration start and a second mapping marks the generated value start against the replaced expression start. This preserves useful stepping without claiming that generated digits or units existed in the source.

For one declaration synthesized from multiple adjacent declarations, the generated property name receives the segment's sole mapping at the start of the validated multi-input causal span. Even when the generated declaration reuses one authored value token verbatim, it receives no inner mapping: the retained authored declarations and transform proof establish provenance, while a second mapping would falsely imply that the generated shorthand structure existed in the source.

Mappings remain ordered four-field Source Map v3 segments with original and generated columns measured in zero-based UTF-16 code units. `sources`, optional `sourcesContent`, and source identity continue to describe the original file only; transforms do not synthesize source content or implicit source-map comments.

### Validation obligations

Each generated-output pass must test decoded mappings in pretty and minified modes, deterministic repeated emission, generated-segment anchoring, source bounds, and mappings for surviving siblings. Source-map tests accompany but do not replace semantic equivalence, idempotence, order, allocation-failure, and independent-output validation.

## Consequences

Positive consequences:

- Debuggers receive honest coarse provenance for generated values instead of misleading precision.
- Generated output cannot smuggle arbitrary bytes through a source span.
- Pretty and minified output share one deterministic mapping rule.
- Later transform types have a consistent causal-anchor policy without changing Source Map v3.

Costs and constraints:

- A generated segment has only a start mapping until a future standard can express richer provenance.
- Passes must carry and validate causal spans through immutable AST reconstruction.
- Some inserted boilerplate will intentionally have no mapping when no defensible authored cause exists.
- Source maps cannot demonstrate semantic correctness; dedicated transform validators remain required.

## Rejected alternatives

- **Map every generated character to the replaced span start.** Rejected because it creates dense but false precision and larger maps.
- **Reuse the closest preceding mapping.** Rejected because adjacency is not provenance and can attribute a generated node to an unrelated declaration.
- **Default generated nodes to source offset zero.** Rejected because it silently points at unrelated source and hides missing provenance.
- **Embed generated CSS as unchecked bytes.** Rejected because source containment would no longer protect parser/emitter invariants.
- **Disable source maps whenever transforms run.** Rejected because conservative causal mappings are useful and independently verifiable.
